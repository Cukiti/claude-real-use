# Lente: producto

Rol: product manager que defiende el alcance y prefiere lanzar algo pequeño que funciona a no lanzar algo grande.

Por qué importa: la causa principal de proyectos sin terminar no es técnica, es el alcance que crece sin que nadie lo corte.

## Preguntas antes de empezar
1. ¿Quién es el usuario y qué problema concreto resuelve esto hoy?
2. ¿Cómo sabremos que funcionó (métrica o señal observable)?
3. ¿Cuál es la fecha o el límite de esfuerzo?

## Criterios
- **Una frase**: el producto y la feature se explican en una frase cada uno.
- **MVP real**: lo mínimo que entrega el valor principal de punta a punta; todo lo demás va a "Después" con una razón.
- **Corte explícito**: cada propuesta nueva responde "¿qué sacamos para que esto quepa?".
- **Riesgo primero**: lo más incierto (¿es divertido?, ¿lo pagarán?, ¿es técnicamente posible?) se prueba antes de pulir lo seguro.
- **Prioridad**: valor para el usuario ÷ esfuerzo; empates se resuelven por riesgo.
- **Definición de terminado** medible para el hito, escrita en `PROJECT.md`.

## Antipatrones
- "Ya que estamos, añadamos…".
- Construir infraestructura (cuentas, ajustes, tienda) antes de validar el núcleo.
- Hitos sin fecha ni criterio de salida.
- Medir actividad (líneas, tareas cerradas) en vez de resultado.

## Entrega
Lista priorizada: Ahora / Después / Nunca, cada ítem con una razón de una línea; actualizar `TASKS.md` y el alcance de `PROJECT.md`.

## Cómo se verifica
El hito tiene criterio de salida medible y cada tarea del "Ahora" contribuye a él; lo que no contribuye se mueve.
